## Decided

Already settled in the design decisions chat, documented in full in `CLAUDE.md`. Listed here for visibility, not to re-litigate.

- Repo layout: single Next.js app, role-based top-level route folders (`app/customer/`, `app/employee/`, `app/owner/`) — not separate apps per role
- Frontend: Next.js, TypeScript, App Router
- Backend/data: Supabase (Postgres, Auth, Realtime, Storage); custom trusted logic (Stripe webhooks, payment intents, slot validation) in Supabase Edge Functions (recommendation scoring turned out to be plain SQL - see "Restaurant recommendations" below)
- Authorization: Postgres RLS keyed off a role claim, not app-level checks
- Double-booking prevention: Postgres exclusion constraint on table/time-range
- Payments: Stripe - test mode / demo only, single account, no split (see the "Payments" note below)
- ML recommendations: pure collaborative KNN on weighted behavior (bookings, favorites, views) with a popularity fallback for new users — built and ranking the customer's browse list; see "Restaurant recommendations" below. `pgvector` turned out not to be needed for it
- Design/color palette: warm orange accent (brighter orange-500/orange-300, dark text on fill) + warm stone neutrals (never black/near-black as a background) + semantic status colors (success/warning/danger, not yet used) — see CLAUDE.md's Design conventions section
- Restaurants table: minimal initial cut (`id`, `owner_id`, `name`, `created_at` only) — no `image`/`address`/`hours`/`description` yet, added when the feature that needs each one is built, not speculatively now. An owner can have more than one restaurant (`owner_id` is a plain indexed FK, not unique). RLS restricts restaurant creation to `profiles.role = 'owner'` accounts, but restaurant rows are viewable by any authenticated user (any role) — needed so customers/employees can browse.
- Employee applications/staff: single `restaurant_staff` table, one row per (restaurant, employee) pair with `status` = `pending` | `accepted`. No `rejected` status — a reject (owner) or cancel (employee) both just delete the pending row, and removing a staff member deletes the accepted row; this keeps the door open to re-apply later without extra status bookkeeping, and nothing in the product needs a record of past rejections. An employee can be staff at multiple restaurants (many rows). Owners manage this per restaurant at `/owner/restaurants/[id]/staff`. Added a narrow `profiles` RLS policy so owners can see the name of anyone with a staff row at one of their restaurants (previously profiles were self-view only).
- Restaurant capacity/hours: `capacity` (nullable int, no cap by default) and `default_stay_minutes` (not null, defaults to 90) added directly to `restaurants`. Working hours are a separate `restaurant_hours` table, one row per day of week (`day_of_week` 0-6 matching Postgres's `extract(dow ...)`, open/close both null = closed that day), so the reservation feature can later join straight against a booking's date. Overnight hours (open past midnight) aren't cross-validated yet — deferred until a restaurant actually needs it. Owner edits all of this (name, capacity, default stay time, per-day hours with an "apply Monday to all" action) at `/owner/restaurants/[id]`.
- Restaurant sections & table layout — structure: two fully independent, optional features; a restaurant can have sections, a table layout, both, or neither. A table optionally belongs to one section via `tables.section_id`, which stays nullable at the DB level even once sections exist — the rule "every table in an active layout must belong to a section once the restaurant has any" is enforced entirely in app logic (checked at save time against the union of active layouts' tables), never a DB constraint. Deliberately no auto-created "default"/catch-all section — if the owner wants an "everything else" grouping they create it themselves like any other section. "Sections can't logically overlap" (e.g. indoor vs. window-seating both describing the same tables) is owner-facing UX guidance only, not something the system validates — a table can reference at most one section by construction, so true overlap can't occur in the data. The table layout builder is a spatial floor-plan canvas (60x40 grid, 24px/unit, snap-to-grid, pans via a shorter fixed-height scrollable viewport) with drag-to-move, resize, marquee multi-select, and bulk section-assign/delete; tables can't overlap (rejected at drag/resize/add time), and a new table inherits the previous one's section and size. Table names are *not* unique (unlike sections/layouts, which are, per restaurant). RLS follows the existing `restaurant_hours` pattern (owner-scoped write, any-authenticated-user read) for `sections`, `layouts`, and `tables` alike — `tables`' insert/update policies additionally verify that `layout_id`/`section_id` belong to the *same* restaurant as `restaurant_id`, not just that `restaurant_id` itself is owned by the caller: since `layouts`/`sections` ids are publicly readable (same any-authenticated-user pattern), an owner could otherwise attach their own restaurant's table to another restaurant's layout or section via a direct API call.
- Restaurant sections & table layout — capacity cascade: "more specific overrides broader," but revised from the original plan to *never overwrite* `restaurants.capacity`/`sections.capacity` except in pure manual mode (no sections, no active layout) — see the implementation note below for why. No sections and no active layout: the columns hold the plain manually-typed numbers, editable as normal. Sections exist, no active layout: each section has its own manually-typed capacity (editable input); the restaurant's total is shown live as `sum` of section capacities, computed fresh on every render — not read from `restaurants.capacity`. Any layout is active: capacity is shown live from the union of every *active* layout's tables (a restaurant can have several active at once, e.g. one per floor) — a section's live capacity = sum of its seats across all active layouts, the restaurant's live total = sum of every active layout's tables — again computed fresh, never read from the columns. Removing the last section, or deactivating/deleting the last active layout, doesn't reseed anything: the manual capacity field/section rows simply become editable again, showing whatever was last actually stored in the database (untouched the whole time it was in derived/live-only mode), not a value freshly computed from what just got removed.
- Restaurant sections & table layout — implementation: `sections` and `layouts` tables (both `restaurant_id`-scoped, `layouts` also has `is_active boolean`), `tables` scoped to a `layout_id`. Everything — name/hours/capacity, sections, layouts (create/activate/deactivate/delete), and the currently-open layout's floor-plan canvas (drag/resize/marquee-select/bulk section-assign, snap-to-grid, no overlap allowed) — lives on one page (`/owner/restaurants/[id]/edit`), staged as one shared local draft and committed together on a single "Sačuvaj izmene". A section/layout/table's local draft `key` is its own real id for anything already saved (never a fresh random id) — this is load-bearing: tables reference a section by that same key, and a random key here breaks both hydration and the live capacity math. `restaurants.capacity` and `sections.capacity` are deliberately **only written to in pure manual mode** — while sections or an active layout exist, the displayed number is always computed live from sections/tables (see the cascade note above) and those columns are left untouched, so a manually-typed number quietly survives being superseded and reappears if sections/active layouts are later removed. This means any code outside this form (e.g. a future customer-facing restaurant listing) can't just read `restaurants.capacity`/`sections.capacity` and trust it — it must compute the effective capacity itself whenever the restaurant has sections or an active layout, the same way this form does.
- Reservation booking: tables are exclusive, not communal — a table hosts one confirmed reservation per time range (the "partially-reservable tables" question this used to leave open is resolved: not for now). `create_reservation()` is a single Postgres `security definer` RPC rather than a Supabase Edge Function, since it's pure check-then-insert against the DB with no third-party API or secret involved — the restaurant row is locked unconditionally before any capacity read, serializing every booking attempt against that restaurant so concurrent capacity checks can't race, with the table-level exclusion constraint as a final backstop. Duration is capped between 30 and 180 minutes independent of restaurant hours, falling back to `restaurants.default_stay_minutes` (now constrained to that same 30-180 range) when left unspecified. Where a reservation is actually seated lives in two child tables (`reservation_tables`, `reservation_sections` — mutually exclusive per reservation, neither used in the plain-capacity baseline case) rather than a column on `reservations` itself, since one reservation can span multiple tables or multiple sections. A section preference is always just that — a preference, never a hard requirement: whether picking tables (once a layout is active) or sections (no layout), the system fills the preferred one first and spills the remainder elsewhere rather than rejecting outright; only an explicit table pick is validated strictly, with no auto-expansion. Capacity follows the existing cascade (active layout > sections > plain `restaurants.capacity`). Two further `security definer` RPCs (`get_occupied_table_ids`, `get_section_remaining_capacity`) let the customer-facing form preview live availability before submitting — without exposing whose reservation occupies what, since RLS otherwise hides other customers' bookings entirely — but that preview is informational only; every actual check still happens server-side in `create_reservation()` at submit time.
- Menu items — schema: `menu_categories` (`restaurant_id`-scoped, `name` + `display_order`, unique `(restaurant_id, name)` per restaurant) and `menu_items` (`restaurant_id`-scoped, optional `category_id` FK — nullable like `tables.section_id`, `on delete set null` so removing a category doesn't delete its items) holding `name`, `description`, `price numeric(10,2)` (checked `>= 0`), `is_available boolean default true`, `display_order`. Single currency (RSD) assumed — no currency column, matching the app being Serbian-only elsewhere. Modifier groups via `menu_item_options` (`name`, `is_required`, `allow_multiple`) and `menu_item_option_choices` (`name`, `price_delta numeric(10,2) default 0`) — e.g. a required single-select "Veličina" group with "Mala/Srednja/Velika" choices, or an optional multi-select "Dodaci" group; these exist now even though ordering itself is still backlog, since the owner needs to define an item's options before customers can pick from them later.
- Menu items — image: `menu_items.image_url` (nullable text) exists in the schema now but the owner has no UI to set it in this pass — deliberately deferred, no Storage bucket wired up yet (upload shipped later — see "Image uploads" below). When null, the app renders a theme-aware inline-SVG placeholder component (`MenuItemImage`) rather than storing or hosting a default image file — the fallback is a client-side rendering concern, not database state. Not used on any page yet (no display surface exists until customer ordering is built), but ready to drop in.
- Image uploads: one **public** Supabase Storage bucket, `restaurant-images`, for both restaurant cover images (new `restaurants.image_url`) and menu item photos (the existing `menu_items.image_url`). Public because these photos aren't sensitive and customers load them constantly — no per-read signing; writes are still owner-only. Objects live at `<restaurant_id>/<random>.<ext>` and storage RLS on `storage.objects` checks ownership of the restaurant named by the first path segment (insert/select/delete only — deliberately no update policy, so an object can't be moved into another restaurant's folder). The column stores the full public URL; the object path is recovered from it when an image is replaced or its item deleted. Images are validated (JPEG/PNG/WebP, ≤15 MB source) and downscaled + re-encoded to JPEG **in the browser** before upload (JPEG rather than WebP: every browser can encode it, whereas some can't encode WebP; transparent images are painted on white first, since JPEG has no transparency; files picked may still be JPEG/PNG/WebP, and the bucket still allows WebP so images uploaded earlier stay valid) (restaurant image max 1600px, menu item max 900px), so no server-side processing is needed and the bucket's own 5 MiB / mime-type limits are only a backstop. The save order is deliberate: nothing is uploaded until the owner saves the surrounding form (`ImagePicker` just holds a pending replace/remove); on save the new image uploads first, the row write follows, and the old object is deleted only after that write succeeds — a failed save removes the new upload rather than leaving the row pointing at a deleted file. Old-object cleanup is best-effort (a failure leaves an orphan, never fails the save). Plain `<img>` (like the existing `MenuItemImage`), not `next/image` — the browser already downscaled, so no `remotePatterns` config is needed. Restaurant images appear on the restaurant cards of all three roles (customer list, employee landing/apply, owner landing) and menu item images on the menu cards; the customer restaurant page itself shows no restaurant image (see "Restaurant/menu card layouts" below). Gotcha found while verifying: inside a storage policy's `exists (select … from public.restaurants r …)` subquery, a bare `name` resolves to `restaurants.name`, not the object's path — the policies must reference `objects.name` explicitly (the first version didn't and denied every write; fixed in `20260919130000_fix_image_storage_policies.sql`). Deleting a restaurant purges its folder (see "Deleting a restaurant" below). Not yet handled: deleting an owner's account — `restaurants.owner_id` cascades from `auth.users`, which removes the rows but not the storage objects, and they stay publicly readable by URL. Account deletion must also remove `restaurant-images/<restaurant_id>/` for each of the owner's restaurants.
- Dropdown menu consistency: `AppHeader` no longer takes a `menuItems` prop — it derives the menu from the current URL's role segment (`menuItemsForPath()` in `src/lib/nav.ts`, replacing the three per-role `*-nav.ts` files), so every page of a role gets the identical menu by construction (previously each page opted in, and the current page's own link was deliberately left out, which made the menu differ from screen to screen). "Početna" (the role's home: `/customer`, `/employee`, `/owner`) is always first, followed by the role's destinations; the current page's entry stays in the list — highlighted with a light accent tint plus `aria-current="page"` and bolder text (not color alone) — and clicking it calls `router.refresh()` instead of navigating. "Current" means an exact path match, so a nested page like a restaurant's menu editor highlights nothing.
- Restaurant/menu card layouts (UI pass after image uploads): role landing pages no longer show a role heading (each keeps a visually hidden `h1` "Početna" so the page still has a heading). Customer restaurant browse and employee apply page are 3-across grids (1 column below `sm`, 2 at `sm`, 3 from `md`) of image-on-top cards; the employee landing stays one card per row (now with the image). The customer restaurant page no longer shows the restaurant image — the menu is the focus, and its items are 3-across cards with a large 16:9 image on top (same shape as the restaurant images) (`MenuItemImage` placeholder now `slice`s to fill any aspect ratio) and name, full description, price and the add button below. The owner landing shows each restaurant as a card: a larger name in the default text color, the edge-to-edge image, then the four actions in the fixed order Rezervacije, Meni, Osoblje, Uredi (defined once in `OWNER_RESTAURANT_ACTIONS`; "Uredi" is a plain orange text link, the others outlined buttons). The whole name section plus the image is one link to the restaurant's reservations page (same target as "Rezervacije"), and hovering it highlights the card border like the customer/employee cards do (via `has-[[data-card-link]:hover]`, since the card itself also holds the action buttons and so can't be the link). The "Dodaj restoran" form matches the list's width (`max-w-lg`) with the input and button on one row. Customer menu item cards keep every collapsed card the same height: the name and the description each take one line (the description's line is reserved even when it is empty), a chevron appears only when text is actually cut off (see `MenuItemCard`), and expanding grows only that card. The customer restaurant list and the employee apply page center their search bar, and restaurant names are slightly larger (customer list, employee landing, employee apply page); the apply page keeps a visually hidden "Prijava u restoran" heading instead of the visible one, like the role landing pages. On the apply page a restaurant name stays on one line and gets an expand chevron only when it doesn't fit (`ExpandableName`, same cut-off detection as the menu cards); expanding grows only that card. On the owner landing, the name section's padding is deliberately small (4px) so the visible gap around the name matches the ~10px around the action buttons. In the owner menu editor, item thumbnails and the image-picker preview are 16:9 (`aspect-video`, `object-cover`) like the customer cards — this is display-only cropping, so existing images (any aspect ratio) and new uploads look the same; the stored image is not cropped. Employee/owner list pages now do show restaurant images, superseding the earlier "dashboard lists show no images" note in the Image uploads entry.
- Menu items — implementation: RLS follows the existing owner-write/any-authenticated-read pattern (`restaurant_hours`/`sections`/`tables`), with the same same-restaurant validation `tables.section_id` has applied to `menu_items.category_id`, and `menu_item_options`/`menu_item_option_choices` inheriting ownership by joining up to `menu_item_id`. Unlike sections/tables' draft-and-commit-together pattern, owner UX here is immediate-save CRUD — add/edit/delete each save independently, like the staff page — since menu items are independent rows rather than a small interdependent set with live capacity math. Lives at `/owner/restaurants/[id]/menu`: categories (add/rename/reorder/delete) and items (add/edit/delete, per-item availability toggle) managed together on one page.
- Customer ordering — cart model: `orders`/`order_items`/`order_item_choices` tables. A customer has at most one `draft` order at a time (partial unique index on `orders (customer_id) where status = 'draft'`), not one per restaurant — starting a cart at a different restaurant replaces the old one (with a confirm dialog client-side first), same behavior as Wolt/Glovo. `order_items.unit_price`/`item_name` are snapshots taken at add-to-cart time (not live references), computed **server-side only** — `add_order_item()` (`security definer`) looks up the current menu item price and every selected choice's `price_delta` itself; the client only ever sends a menu item id, chosen option-choice ids, and a quantity, never a price. Adding an already-in-cart item with the same options again increments that line's quantity instead of creating a duplicate row. `order_items.quantity` is the only thing a customer can change directly afterward, on a `draft` order only — enforced by a `BEFORE UPDATE` trigger comparing OLD/NEW (a column-level grant was tried first and didn't reliably close the gap; see the migration history for `order_items`' update policy). `menu_item_id` is nullable with `on delete set null` (not cascade), so a historic order line survives the owner later deleting that menu item, keeping its snapshotted name/price.
- Customer ordering — confirmation flow: the customer's flow is menu (browse, add to cart) → one combined page at `/customer/restaurants/[id]/reserve` with the existing reservation form, a read-only cart summary, and a payment placeholder (no real Stripe integration yet — see "Pay by debit card" in the backlog). The single confirm button is the only moment anything commits: `create_reservation()` was extended with an optional `p_order_id` so the same call creates the reservation *and* finalizes the linked order (status → `confirmed`, `reservation_id` set) atomically — re-validating the cart is non-empty and every line's item is still available before committing, and rolling back everything (including the reservation) if not. RLS on the three new tables mirrors `reservations`: a draft order is private to its customer; once confirmed, the restaurant's owner/accepted staff can see it too.
- Customer past/current reservations: "current" vs "past" is purely time-based, not status-driven — current = `status = 'confirmed' AND ends_at >= now()`, past = everything else (including a cancelled-or-no-show reservation whose time hasn't arrived yet, and any reservation whose time has passed regardless of status). This was chosen over a status-driven split specifically to avoid needing a mechanism (cron/edge function/lazy update) to flip `confirmed → completed` once `ends_at` passes — nothing sets `completed` anywhere in the app today, and adding that machinery wasn't justified just for this display. The linked order (if any) is shown inline on each reservation card via the existing `orders.reservation_id` reverse join and the same read-only `CartSummary` component the reservation-confirm page already uses — no new query pattern. Display-only for now: no cancel action here, matching "Cancel a reservation" staying its own separate backlog item. Lives at `/customer/reservations`, reachable via a "Moje rezervacije" entry in `AppHeader`'s dropdown menu (a new optional `menuItems` prop, shared across customer pages via `src/lib/customer-nav.ts`) rather than a standalone button. Each card's linked order is collapsed behind a toggle rather than shown open by default.
- Table/section deletion and capacity guards: found while building the customer reservations page above — `reservation_tables.table_id`/`reservation_sections.section_id` are both `on delete cascade`, so nothing stopped an owner from deleting a table/section (or shrinking `restaurants.capacity`/`sections.capacity`) out from under a confirmed, not-yet-ended reservation; the reservation row would silently survive with `status` still `confirmed` but no seating record at all. Fixed with four triggers (`supabase/migrations/20260913140000_protect_capacity_from_active_reservations.sql`, see `SCHEMA.md`'s "Deletion/capacity guards" callout): a table/section delete is rejected outright while an active reservation (`status = 'confirmed' and ends_at >= now()`, same rule the reservations page itself uses) references it, and a capacity decrease is rejected below the *peak* concurrently-committed load — computed via a sweep-line over overlapping confirmed reservations' time ranges, not just each one checked in isolation, since several can overlap and their party sizes must be summed at the moments they overlap. Deliberately DB-level (triggers), not just a client-side check, since the owner's save form talks to Supabase directly with no server-side gate in front of it. The owner's edit form surfaces the raised message verbatim (`raisedMessageOr()` in `edit-restaurant-form.tsx`, matching the existing `error.code === "23505"` pattern) instead of a generic save-failed string.
- Table/section deletion guards — error detail: follow-up once the guards above were shown to the owner in practice - a bare "can't delete" message doesn't say *which* table/section, or *why* (`supabase/migrations/20260917100000_detailed_active_reservation_errors.sql`). The delete-blocking triggers' raised messages now name the specific table/section and its earliest active reservation's date/time and party size. Since a trigger only reports the first blocking row it hits (aborting the whole statement there), and the owner's "Sačuvaj izmene" can remove several tables/sections in one save, two new functions (`tables_with_active_reservations`/`sections_with_active_reservations`) let the form check every candidate id *before* attempting any delete, so a single save reports every blocker at once instead of the owner discovering them one retry at a time. The DB triggers remain the authoritative enforcement either way - the pre-check is purely a UX improvement, not a trust boundary.
- Table/section deletion guards — layout grouping and a real corruption bug: two more follow-ups. (1) Table names are only unique per *layout*, not per restaurant, so once a blocked-tables message spans more than one layout, a flat list is ambiguous about which layout a given table name belongs to - `tables_with_active_reservations()` now also returns each blocked table's layout name (`supabase/migrations/20260917110000_tables_with_active_reservations_layout_name.sql`), and the owner form groups its message by layout ("raspored1: ...; raspored2: ...") whenever more than one is involved, falling back to the simpler flat list otherwise. (2) The capacity-decrease trigger, once live, exposed a real bug in the section-save flow: a changed section is renamed to a temp `__tmp_<id>` placeholder first (to avoid transiently colliding with another section being renamed in the same save), then a second statement sets its real name *and* capacity together - if that second statement is rejected by the capacity trigger, the temp-rename from the first statement had already committed with nothing to roll it back, leaving the section stuck on its temp name. Fixed by pre-checking every section whose capacity is decreasing *before* the temp-rename dance starts at all (`sections_peak_reserved_capacity()`, `supabase/migrations/20260917120000_sections_peak_reserved_capacity_batch.sql`), naming every section that would fail (and by how much) in one message, exactly like the deletion pre-check above. This narrows the corruption window a lot but doesn't close it completely - see the next entry for the full story and the residual gap that's still open.
- Code-review follow-up on the two entries above: two real issues found reviewing this branch, both fixed. (1) `tables_with_active_reservations()`/`sections_with_active_reservations()`/`sections_peak_reserved_capacity()` were `security definer`, granted to `authenticated`, with no ownership check at all - since `tables`/`sections` are public-read, any logged-in customer or employee could pass an arbitrary table/section id from *any* restaurant and learn a stranger's reservation time and party size, bypassing the RLS that normally restricts that to the customer who owns it, the restaurant's owner, and accepted staff. Fixed in `supabase/migrations/20260917130000_scope_capacity_functions_to_owner.sql` by joining each function up to `restaurants` and requiring `owner_id = auth.uid()` - a table/section belonging to someone else's restaurant now just doesn't appear in the result, instead of leaking it. (2) The section-capacity pre-check (previous entry) still had a real TOCTOU gap: it originally ran once, at the very top of `handleSubmit`, with several other awaited Supabase calls (layout/hours/restaurant-name writes) happening before the actual rename-then-update dance it was meant to protect - a new reservation landing in that window could still make the real update fail and leave the section on its `__tmp_<id>` name, just less often than before. Narrowed two ways: the pre-check now runs immediately before the rename dance instead of at the top (minimizing, not eliminating, the gap - there's still one network round-trip between "checked safe" and "written"), and the temp-rename step itself now only touches sections whose *name* is actually changing (not every section with any change), since a capacity-only save never needed the rename in the first place. A fully atomic fix (one server-side transaction covering validation + rename-swap + update) would close this completely but wasn't done here - worth doing if this keeps coming up in practice.
- Reservation status lifecycle: extends `reservations.status` beyond plain `confirmed`/`cancelled`/`completed`/`no_show` with a service-flow state machine driven by accepted staff (not the owner) - `confirmed -> [preparing_order -> order_prepared ->] ongoing -> completed`, plus `confirmed`/`order_prepared -> no_show` only once `starts_at` has passed. `preparing_order`/`order_prepared` only apply when the reservation has a linked confirmed order, otherwise the flow skips straight to `ongoing`; skipping stages when an order does exist is rejected, not silently allowed. `cancelled` stays unreachable through this RPC - a customer-initiated cancel is still its own backlog item. "Active" (occupying a table/section - every capacity/availability function and delete/capacity-decrease guard) is now `is_active_reservation_status(status)` rather than a hardcoded `status = 'confirmed'`; capacity/table availability rolls off on its own once `ends_at` passes (the existing `... and ends_at >= now()` pattern), but the *status label* doesn't, so a `pg_cron` job (`finish_expired_reservations()`, `20260918120000_auto_finish_reservations.sql`, every minute) sets it: `ongoing` → `completed`, and any still-waiting status (`confirmed`/`preparing_order`/`order_prepared`) → `no_show`. Staff who forget to mark a seated party `ongoing` will see it recorded as a no-show - accepted, staff are expected to keep statuses current. What to do about an uncollected, possibly paid/prepared order on a no-show is undecided (payment is still a placeholder; revisit when Stripe lands). *Early* completion/no-show (before `ends_at`) does need one, since the `reservation_tables` exclusion constraint has no idea what `status` means and would otherwise keep blocking the rest of the original slot - `update_reservation_status()` shrinks `ends_at` on both `reservations` and `reservation_tables` down to (approximately) `now()` in that case. The mirror case: marking a reservation `ongoing` before its booked `starts_at` moves `starts_at` up to `now()` (same two places; `20260918100000_ongoing_moves_start_to_now.sql`), so an ongoing reservation has always genuinely started and an early completion can never produce `ends_at < starts_at` (the `ends_at` clamp to at least `starts_at + 1s` stays as a cheap guard). Pulling `starts_at` earlier is deliberately limited (code-review follow-up, `20260918130000_reservation_lifecycle_review_fixes.sql`): only within 60 minutes of the booked start - a mistaken tap on a reservation days out would otherwise permanently rewrite its start with no undo - and the employee UI asks for confirmation first; it's also rejected, with readable messages, when another reservation already holds one of its tables in the gap (the exclusion constraint). Once `ends_at` has passed no transition is accepted at all (the cron sweep is about to finish it). The same review revoked `update_reservation_status()` from `anon`/`public` and the two singular peak-capacity functions from every app role (they leaked any restaurant's peak booked load and are only ever reached through triggers), and added a partial index for the sweep. **Known gap:** section-based and plain-capacity reservations have no exclusion constraint, so starting one early is *not* re-checked against capacity for the newly-occupied `[now, old starts_at)` window - it can briefly overbook there. Fixing it means re-running the capacity check in `update_reservation_status()` for those modes; not done yet. All of this lives in one RPC (`update_reservation_status()`, `supabase/migrations/20260917140000_reservation_status_lifecycle.sql`) rather than a raw RLS update grant, matching `create_reservation()`'s own reasoning: the transition graph is real validation logic a plain policy can't express. **Undo (`20260919170000_reservation_status_undo.sql`):** the same RPC also allows two one-step-at-a-time steps back before the guest is seated — `order_prepared -> preparing_order -> confirmed` — deliberately status-label-only: all three statuses are active and share one time range, so neither touches `starts_at`/`ends_at`/`reservation_tables` and there is no exclusion or capacity check to redo. It does not jump (`order_prepared -> confirmed` is rejected), and `ongoing`/`completed`/`no_show`/`cancelled` can't be stepped back from. - Reservation cancellation (`supabase/migrations/20260919100000_cancel_reservation.sql`): one `security definer` RPC, `cancel_reservation()`, callable by the reservation's customer **or** the owner of its restaurant — not by staff (they run service, they don't drop bookings) and not by `anon`. Allowed only from `confirmed`/`preparing_order`/`order_prepared` (before the guest is seated), with no cutoff relative to `starts_at`, and never once `ends_at` has passed (same "the cron sweep is about to finish it" reasoning as `update_reservation_status()`). The permission check is folded into the row lookup, so a missing id and someone else's id give the identical "doesn't exist" error — no id oracle. Freeing the slot follows the early-completion pattern (the exclusion constraint on `reservation_tables` still isn't status-aware) but with one deliberate difference: a cancelled reservation is usually still in the *future*, so shrinking `ends_at` to `now()` alone would put it before `starts_at`, and shrinking to a tiny non-empty range instead (e.g. `[now() - 1s, now())`) could collide with another reservation running on that same table right now (exclusion violation, cancel fails). So both `starts_at` and `ends_at` on the `reservation_tables` rows are set to `now()`: an *empty* range, which overlaps nothing, can't violate the constraint against anything, and never has `starts_at > ends_at`. The `reservations` row itself is **not** shrunk — its `ends_at > starts_at` check rules out an empty range, nothing reads a cancelled reservation's range (every capacity check filters on `is_active_reservation_status()`), and leaving it means a cancelled booking still shows the time it was booked for in the customer's/owner's history. - Deleting a restaurant: every child table cascades from `restaurants`, so a bare delete would wipe customers' reservations and orders (and, with Stripe, the financial records). `delete_restaurant(id)` (owner only, `security definer`, locks the restaurant row like `create_reservation()` does) therefore decides in the database: refused while any reservation is active (`confirmed`/`preparing_order`/`order_prepared`/`ongoing`); really deleted when the restaurant has no reservation history at all (draft carts don't count); otherwise **archived** (`restaurants.archived_at`) - its staff rows and draft carts are removed, its reservations and orders stay for the customers' histories. Hard delete is only reachable with zero reservations, which also sidesteps the `orders.reservation_id` RESTRICT and the tables/sections delete-guard triggers depending on cascade order. Direct deletes from the Data API are closed (grant + policy dropped) and `restaurants` updates became a column-level grant (like `profiles.role`) so `archived_at` can only be set by the function - a column added to `restaurants` later must be added to that grant. Archived restaurants are hidden by an explicit `.is("archived_at", null)` on every restaurant-listing/lookup query (owner pages, customer browse/map/detail/reserve, employee apply list, owner all-reservations view) rather than by RLS: the public select policy stays as is so a customer's history can still show the name, and a filter in RLS would risk the cross-table recursion (`42P17`) - **a new query over `restaurants` must add that filter**. New reservations/carts/staff applications at an archived restaurant are rejected by one `before insert` trigger on the three tables (rather than editing `create_reservation()`/`start_cart()`). Image files: Storage does not cascade and the storage delete policy checks ownership through the restaurant row, so the Server Action (`deleteRestaurantAction`) purges the `restaurant-images/<id>/` folder *before* the row goes, on the no-history path only, and aborts (nothing deleted) if the purge fails; archiving keeps the files. `cancel_all_active_reservations(id)` (owner only) loops `cancel_reservation()` over the cancellable reservations - ongoing ones (guest already seated) are skipped and keep blocking deletion until staff complete them. UI: type-the-name confirmation on the edit page; the danger section shows counts of what is lost, or the blocker with a link to the reservations page. - Account deletion: a bare `delete from auth.users` cascades into other people's data - a customer's reservations/orders would vanish from restaurants' history (and, with Stripe, the financial records), and an owner's restaurants would take every customer's reservations at them along. So `delete_my_account()` (`20260919200000_account_deletion.sql`; caller only, no id parameter, `security definer`) decides in the database, and the three foreign keys that would have cascaded now **detach**: `reservations.customer_id` and `orders.customer_id` are nullable `on delete set null` (the customer's history is **anonymized**, not erased - those rows hold no name/phone/notes, the profile goes with the user; the owner's list shows "Obrisan korisnik"), and `restaurants.owner_id` is nullable `on delete set null` (only archived restaurants can be left pointing at a deleted owner, since every live one is deleted or archived first, so nothing live is ever ownerless). This also retires the `orders.reservation_id` RESTRICT hazard the backlog item worried about: no reservation or order row is deleted by an account deletion any more. **Refused while anything is active** (same definition as `delete_restaurant()`: an active status and `ends_at` still in the future): a customer's own bookings (an ongoing one can't be cancelled by the customer, so it blocks until staff complete it) and any owned restaurant's, with Serbian `P0001` messages; the page shows the blocker with links (`/customer/reservations`, or `/owner/restaurants/[id]/reservations`, which has "Otkaži sve rezervacije"). Otherwise an owner's restaurants each go through `delete_restaurant()` (deleted if no history, archived otherwise), draft carts are deleted (private, meaningless without a customer), and employees just lose their staff rows. The `auth.users` row is locked `for update` first: a booking insert takes `for key share` on it via the FK, so a concurrent booking either lands before the active-reservation check or fails its FK - no active booking is left ownerless. `account_deletion_plan()` feeds the page (role, active bookings, history left behind, blocking restaurants, ids to delete/count to archive). Deletion is a SQL function rather than a service-role Server Action, so deletion itself needs no service-role key and reuses `delete_restaurant()` as is (the app has since gained a service-role key, but only for email changes - see the account editing entry below; deletion deliberately doesn't use it). **The password re-check is app-level, not a security boundary**: `deleteAccountAction` (`src/lib/auth/delete-account.ts`) verifies it on a throwaway `persistSession: false` client (so the real session cookies aren't rotated) but the RPC stays callable by `authenticated`, so a stolen session could skip it - as it could any other action that account can take; the stricter alternative (revoke execute, call through a service-role client after the check) would need an `auth.uid()`-free variant of `delete_restaurant()` and make deletion depend on the service-role key being set. Storage: deleting `storage.objects` rows in SQL leaves the files, so the Server Action purges the `restaurant-images/<id>/` folders of the restaurants the plan says will be really deleted *before* calling the RPC (archived ones keep their files, like `delete_restaurant()`), and aborts with nothing deleted if a purge fails; if the RPC then fails, some live restaurants have lost their images, tolerated for the same reason as in restaurant deletion (the image components fall back to the placeholder). UI: a "Moj nalog" entry in every role's `AppHeader` menu (`nav.ts`) opens `/customer|employee|owner/account` - account details plus a "Brisanje naloga" section (type your email + password), one shared `AccountDetails` component behind three thin role pages; on success it lands on `/login?deleted=1`. **Stripe follow-up:** when payments land, `delete_my_account()` is where the Stripe customer object has to be handled; the anonymized orders are the retained financial records.
- Account editing and input validation: the "Moj nalog" page (`EditAccountSection`, above the deletion section) edits first/last name, email, phone and password through `updateAccountAction` (`src/lib/auth/update-account.ts`). **No migration**: name and phone are `profiles` columns the existing column-level update grant already allows, and email/password go through Supabase Auth. **The current password is required to change email, phone or password** (not a name) - checked with the shared `verifyPassword()` (`src/lib/auth/verify-password.ts`, extracted from account deletion): a throwaway `persistSession: false` client, so the real cookies aren't rotated. A **password-only** change is made *through that verifier's fresh session*, not the cookie session, because Supabase's "secure password change" wants a recent sign-in and a months-old cookie session isn't one; the cookie session is untouched and other sessions stay signed in. An **email** change (with the new password in the same call, if any) goes through the admin API instead - see below. As with deletion this is a misclick/unattended-browser guard, not a boundary (a stolen session can still call the Auth API and update `profiles` directly). Order: validate everything, then the auth change (the step Auth can refuse, e.g. a taken email), then the `profiles` write, so a refused email leaves nothing half-saved; the reverse failure is reported as such. **Email changes are applied directly, with no email**: Supabase Auth's own `updateUser({ email })` sends confirmation messages even though "Confirm email" is off for signup (seen on the hosted dev project: `email_change_sent_at` gets set), the built-in mailer allows only a few a hour (`over_email_send_rate_limit`), and the change only takes effect once a link is clicked - none of which the app wants, since it doesn't verify emails at signup either. So `updateAccountAction` calls `updateUserEmailAsAdmin()` (`src/lib/supabase/admin.ts`, `auth.admin.updateUserById` with `email_confirm: true`, the new password in the same call if there is one, so it is atomic). **This is the only use of the service-role key** (`SUPABASE_SERVICE_ROLE_KEY`, server-only, never `NEXT_PUBLIC_`): the module exposes one narrow operation on the user id from the server-verified session, starts with `import "server-only"` (a Client Component importing it, directly or indirectly, fails the build - checked in dev), and `update-account.test.ts` pins down that the current password is verified before the admin call and that only the session's user id is used, and if the key isn't set the action shows "Promena emaila trenutno nije dostupna" while everything else keeps working. A password-only change still goes through the verifier's session. Consequences: the address is not verified as a mailbox (same as signup), and the key must be set in every environment that should allow email changes. Auth error codes map to specific messages through `describeAuthError()` (`src/lib/auth/auth-errors.ts`, used by signup and the account form): email already registered, address refused, weak/same password, the two rate limits; unknown codes are logged (code + status, never the address) and shown generically. **One validation module**, `src/lib/validation.ts` (pure, unit-tested), used by the signup page (client-side only - it calls Auth directly, so a hand-made request can still skip it), the account form (instant feedback) and the Server Action (the copy that counts): **email** = RFC 5322 dot-atom local part, then after the `@` one or more letters/digits/`-`/`.` followed by `.` and a TLD of 2+ letters (or a punycode IDN TLD), so `a@a` - which `type="email"` accepts, and two such accounts exist - and `a@b.c` are rejected; each dot-separated part must also be a well-formed DNS label (non-empty, no leading/trailing `-`), which the plain pattern alone would not enforce (`a@b..rs`); lower-cased; **phone** = Serbian numbers (`0xx…`, `+381…`, `00381…`, mobile `6x` or landline `1x-3x`, 8-9 digits after the country code) or any other `+`/`00` E.164 number (8-15 digits), formatting characters ignored, **stored canonical E.164** (a number with no `+`/`00` must start with 0 and is read as Serbian); **names** = letters of any script separated by single space/hyphen/apostrophe, dots allowed between letters and at the end of a word for initials (`J.R.R.`), max 50, whitespace collapsed; **password** = 6-72 bytes (unchanged minimum); the signup page now asks for it twice (`validatePasswordConfirmation()`, also used by the account form). **Only changed fields are validated** (`accountChanges()`): an account from before these rules keeps its `a@a` or `0601234567` and can still edit its name, and a phone re-typed with different spacing counts as unchanged. Deliberately not done: a DB `check` on `profiles.phone`/name (would need the pgTAP fixtures' `555-…` phones and existing rows dealt with), so signup validation is client-side only for now.
- Restaurant recommendations — algorithm (`20260920120000_recommendation_scoring.sql`; built, see the implementation entry after the signals one): **pure collaborative filtering**, user-user KNN over each customer's weighted affinity vector, cosine similarity. Not content-based (restaurants have no cuisine/price/tags to embed), so **`pgvector` isn't needed** — the vectors have one mostly-zero dimension per restaurant, better served by a SQL function than an embedding index (`sparsevec` if it ever outgrows that); this supersedes the older "schema should accommodate `pgvector`" line above, which fits a later content-based/hybrid piece if one is added. **Affinity of a customer for a restaurant** = sum of decayed event weights: reservation `completed` 5, other active reservation 4, a linked order +1, favorite 3, page view 0.5 each **capped at 2 in total per pair** (so any number of views stays below a single booking), `no_show`/`cancelled` 0. **Recency:** each event is multiplied by `0.5 ^ (age_days / half_life)` with a single half-life per profile (an earlier version used two, a slow one for finding similar customers and a fast one for scoring; they were merged in `20260925100000`). Reservation age is measured from `starts_at` (a future booking has age 0); a view's age from `last_viewed_at` (pair-level, coarse but they're the weakest signal). **Neighbors:** the k customers most similar to the caller (cosine similarity over their affinity vectors), counting only customers with at least one *completed* booking (see the sybil note below). **Cold start:** a customer with no affinity at all gets popularity (decayed affinity summed over all users, non-archived restaurants only); everyone else gets a **smooth blend** of KNN and popularity weighted by confidence `total / (total + c)`, so a single page view doesn't flip them into unreliable neighbors; popularity also fills the tail, so the list is never short and a brand-new restaurant nobody has touched can still surface. **Repeat visits are not penalized** (an earlier version marked a recently booked restaurant down by up to 30%; that was removed in `20260925100000`, see the simplification entry below). **Demo profile:** the algorithm must be visibly volatile for demonstrations, so every parameter lives in one config with a `realistic` and a `demo` set (half-life 60 → 14 days, k 30 → 4, blend `c` 10 → 2, so one booking moves a user ~67% of the way to personalised results) - same code, different constants; the weights above are the same in both. It is computed **on request** by a SQL function, not precomputed nightly, so a new view or booking can change the next page load. The only explanation the app shows is the personalization percentage above the list (per-card hints were removed in `20260925100000`); it never carries another customer's identity or bookings. Evaluation idea: time-based holdout (build on data before a cutoff, check whether what people booked afterwards is in their top-k).
- Restaurant recommendations — signals (`20260920100000_recommendation_signals.sql`): two new tables collect the cheap signals, so a new customer can leave the cold start without booking first. `favorites` (`user_id`, `restaurant_id`, `created_at`; a toggle, plain owner-write RLS with no update grant) and `restaurant_views` (`view_count` + `last_viewed_at` per pair — a counter, not a row per view, for bounded growth; written only by the `record_restaurant_view()` RPC, since a counter upsert is what an RLS policy can't express and an update grant would let a client set the count). Both are **private to the customer** (no owner/staff policy) and **deleted, not anonymized, with the account** (`on delete cascade` from `auth.users`, so `delete_my_account()` needed no change) — unlike reservations, whose history has value to the restaurant, a browsing trail has none. Customer-role accounts only; no favorite/view for an archived restaurant (a shared `before insert` trigger for favorites, an explicit check in the RPC). `record_restaurant_view()` is deliberately **not deduplicated by time window**: the per-pair view cap bounds what spamming can achieve, and a window would only make viewing's effect harder to see in a demo. Bookings need no new table — the algorithm reads `reservations`. The tables are read only by the scoring functions (`security definer`, returning restaurant ids and scores only), and any reader must filter `archived_at is null`. The customer restaurant page now has the favorite toggle and records the view (see the implementation entry below).
- Restaurant recommendations — implementation, and what was decided while building it: five functions. `recommendation_params(profile)` holds the two parameter sets, `recommendation_decay()` is `0.5 ^ (age / half_life)`, `restaurant_affinities(half_life, as_of)` builds the weighted, decayed (customer, live restaurant) affinities, `recommendation_scores(user, profile, as_of)` is the algorithm (neighbors, KNN score, popularity, blend, ranking) and `recommend_restaurants()` is what the app calls: the caller's own ranking, customer-role accounts only, always for `auth.uid()` and never a user id from the request; it takes no profile argument. Everything but the last is **internal - executable by no app role**, because scoring takes any user id and reads everyone's behavior. **What the app can read** (narrowed after review, `20260920130000_recommendation_review_fixes.sql`): `rank`, `restaurant_id` and `personalization` only (`20260925100000` removed `similar_users`, `booked_before` and `popular`); a pgTAP test pins that exact shape. The first version also returned `score`, `knn_score` and `popularity_score`, and that was a privacy leak: `knn_score` is the neighbors' own recency-weighted activity scaled to 0..1, so a probe account that made one victim its only neighbor could read the victim's profile off it (reproduced on the dev database), and a `p_profile` argument gave a second, differently-decayed measurement. Both are gone. **Residual leak:** the order itself depends on other customers' behavior (the exact neighbor count and the popular flag that used to leak in very small groups went away with the per-card hints in `20260925100000`). **Sybil steering - closed for accounts without a completed booking** (`20260920150000_recommendation_neighbors_need_bookings.sql`): cosine similarity ignores how much evidence an account has, so throwaway accounts (signup is open, email confirmation is off) that each viewed or favorited one restaurant looked maximally similar to whoever shared it and could crowd real neighbors out of the top-k (reproduced: four one-view accounts moved Ana's first place from Osaka to Sakura, with `similar_users` going from 2 real neighbors to 4 fake ones). A first fix weighted each neighbor's similarity by how much evidence stood behind it (`20260920140000`); review showed it was too weak. An account favoriting about four restaurants (the victim's two, the target and a decoy) beat a real neighbor's weight (0.354 against 0.385), and because `knn_score` is divided by its maximum the weighting cancelled out completely when the caller had no real neighbor, so one fake could become the sole neighbor of a customer with a niche history. It was replaced by a single rule: **only customers with at least one *completed* booking can count as similar to someone.** Views and favorites are free to fake, an upcoming or ongoing booking is nearly as free (`create_reservation()` is open to any customer account and the booking can be cancelled afterwards), and cancelled or no-show ones count for nothing; a completed booking needs the restaurant's staff to have seated the party. Customers without one are still recommended things normally - they just cannot be someone else's neighbor. The rule has no tuning numbers (the evidence formula's `evidence_lambda` and `signal_trust` are gone). **Still open:** an attacker who gets bookings genuinely completed (that takes a restaurant and a staff account of their own), and **popularity poisoning** - the cold-start ranking sums everyone's activity, free accounts included, so an army of accounts favoriting one restaurant still moves it (not reproduced). Those need account-level defenses (email verification, signup and booking rate limits, anomaly detection), not a scoring rule. The count leak that used to be a separate issue is gone together with the per-card hints. The active profile is the single row in `recommendation_settings` (not reachable from the Data API), and it **ships as `'demo'`** because the algorithm is being demonstrated before it has traffic: flip it with `update public.recommendation_settings set profile = 'realistic'` before real use. Choices made in the build that the design left open: **ties are broken by restaurant name**, so with no data at all the list is exactly the alphabetical one the app showed before ranking existed; **favorites fade with the same half-life as everything else** (a standing statement, but not forever); **popularity sums everyone's decayed affinity, the caller's own included**; a customer **nobody is similar to gets personalization 0** however much history they have (a ranking with no neighbors is popularity anyway). (The repeat-visit penalty this entry originally described was removed in `20260925100000`.) It is computed on request from all events (one pass over them since `20260925100000`): fine at demo scale, and the point to precompute is a few tens of thousands of events. **UI:** the customer home (`RestaurantList`) calls `recommend_restaurants()` alongside the alphabetical restaurant query and reorders by rank, falling back to the alphabetical list if the call fails; the page says how much of the order is personalised in one line above the list (the per-card hints were removed in `20260925100000`; `src/lib/recommendations.ts`, unit-tested). The restaurant page has a favorite toggle (`FavoriteButton`: one constant label "Omiljeno" with `aria-pressed` carrying the state, plus the heart's fill - so the state is not color alone and a screen reader does not hear a label that contradicts it; `aria-disabled` rather than `disabled` while a request is in flight, so it keeps keyboard focus) and records a view when opened (`RestaurantViewTracker`): from an effect, not the server render, so a prefetch or crawler doesn't count, with a ref (per restaurant) so React Strict Mode's dev double-mount doesn't count a visit twice. The ranked list refreshes itself when a view or favorite was recorded since it was last shown (`RefreshWhenSignalsChange` plus a flag in session storage, `src/lib/recommendation-signals.ts`): the browser's Back button reuses the page it left, and a back/forward-cache restore remounts nothing, so without it the list stayed stale after a view; the header's back arrow re-renders on its own. A failed `recommend_restaurants()` call is logged before falling back to the alphabetical list. **Demo data:** `supabase/demo/recommendation-demo-seed.sql` (a script, not a migration; run it with `npx supabase db query --linked -f supabase/demo/recommendation-demo-seed.sql`) creates a password-less owner and 5 customers (`demo.*@seed.local`, nobody can sign in as them) and 6 restaurants in two taste groups (Asian: Sakura Sushi, Tokyo Ramen, Osaka Izakaya; grill: Gaucho Steakhouse, Parrilla Grill, Bife Bar) with backdated bookings, favorites and views - small enough to write on a slide. It is idempotent: re-running refreshes the timestamps, removes anything booked at the demo restaurants, and clears the test customer's favorites and views so a demo starts from no history. The demo walk-through and its percentages are in the simplification entry below. **How it was verified (before the simplification; the current suite is described in the entry below):** the pgTAP file `supabase/tests/180-recommendation-scoring.sql` (fixed instant, edge cases: no_show/cancelled, order bonus, view cap, horizon, archived and anonymized data, `k`, permissions; runs only in CI here, its fixtures were replayed against the dev database in a rolled-back transaction to read the pinned values off real output); and an independent reference implementation written from the design (a throwaway script, not in the repo) compared with the SQL output for 13 customers under both profiles, 2002 comparisons, all matching; and the live flow in the browser as the cold test customer. After the review, the pgTAP files 160/170/180 were also executed for real against the dev database (pgTAP is installed there; each run is one `DO` block that always ends in an exception, so nothing commits), and the scoring assertions were mutation-tested: ten deliberate breakages of `recommendation_scores()` (penalty removed, `booked_before` ignoring status, unweighted similarity, a missing norm, the old all-signals penalty, slow-half-life popularity, neighbors without a completed booking, an upcoming booking also qualifying, `k` ignored, confidence from the fast total) are all caught, four of which the first version of the suite let through; the sybil scenarios (four one-view accounts, two accounts favoriting four restaurants each, an account with only an upcoming booking, and a niche customer whose only would-be neighbor is a fake - on restaurants of their own) are part of `180-recommendation-scoring.sql`.
- Restaurant recommendations — simplification (`20260925100000_simplify_recommendations.sql`): the algorithm, and what the app shows of it, were cut down so that it can be explained in a few sentences (the thesis describes it). **Removed:** (1) the repeat-visit penalty - a recently booked restaurant is no longer marked down by up to 30% (`own`, `repeat_penalty`, `repeat_scale` and `restaurant_affinities()`'s `booking_affinity` column are gone); (2) the second half-life - one `half_life_days` per profile now fades bookings, favorites and page views alike, similarity and scores are built from the same affinities, and `restaurant_affinities(half_life, as_of)` takes one half-life and is called once; (3) the per-card hints - `recommend_restaurants()` returns only `rank`, `restaurant_id` and `personalization` (the same on every row of one customer's list), the `similar_users`, `booked_before` and `popular` columns, the `visited` CTE and the neighbor counting are gone, the cards show only the restaurant's name and image, and one line above the list keeps saying how much of the order is tailored to the customer (`describeOrdering()`; `describeRecommendation()` and its tests are gone). **Kept:** the weights (completed booking 5, other active booking 4, +1 with a confirmed order, favorite 3, page views 0.5 each capped at 2 per restaurant), the rule that only customers with a completed booking can count as similar, the blend `personalization = total / (total + blend_c)`, popularity as the fallback, ties broken by restaurant name. **Parameters:** demo - half-life 14 days, k 4, blend_c 2; realistic - half-life 60 days, k 30, blend_c 10. The demo profile stays visibly volatile because k and blend_c are small: for a customer with no history the personalization share is 0% at first, about 20% after one page view of a restaurant (0.5 / (0.5 + 2)), about 33% after a second view (each of the first four views adds 0.5, the cap is 2 per restaurant), about 67-69% once it is also a favorite (67% with two page opens, 69% with three), about 80-81% after a booking, and each step reorders the demo list (the restaurant the customer engages with rises and the restaurants of its taste group follow it). **Measured in the browser** as a fresh customer on the demo data (open Sakura Sushi, back to the list, open it again, open it a third time and press the favorite button, then book a table for two): 0% -> 20% -> 33% -> 69% -> 81%, Sakura Sushi going from 3rd to 2nd to 1st place and Tokyo Ramen entering the top three after the favorite. The percentages come from fresh events, which barely fade, so they are the same for half-lives of 7, 14 and 30 days; 14 was chosen because it keeps a clear recency gradient on the demo data (yesterday's booking weighs about 0.95, one from 25 days ago about 0.29) and keeps the grill-group customer's top result a restaurant they never booked. **What changes for users:** a restaurant the customer has just booked can stay at the top of their list (nothing marks it down any more) and nothing labels an already-visited one. **Verification:** `180-recommendation-scoring.sql` was rewritten for the simplified function (57 assertions: pinned scores for two demo customers, the hub (which pins `k`) and the sybil victim, the completed-booking rule, the wrapper's result shape) and executed for real against the dev database together with `160` and `170` (each run is one `DO` block that always ends in an exception, so nothing commits); ten mutations of `recommendation_scores()` (unweighted similarity, a missing norm, no completed-booking rule, an upcoming booking qualifying, `k` ignored, full trust in neighbors, an inverted blend, the caller as their own neighbor, unscaled popularity, a repeat-visit penalty coming back) are all caught; and an independent Node reference implementation of the simplified algorithm matches the SQL on 1430 comparisons across 13 customers and both profiles.
- Unique restaurant names (`20260920110000_restaurant_name_unique.sql`): live restaurants can't share a name, **across all owners** (customers find restaurants by name and two identical cards are indistinguishable), **compared after normalization** (`normalize_restaurant_name()`, `20260920130000_recommendation_review_fixes.sql`: invisible zero-width characters removed, Unicode NFKC - which turns every exotic space into a plain one - lower-casing, Serbian Cyrillic transliterated to Latin, whitespace collapsed and trimmed; a plain `unique(name)` would allow a look-alike differing by a capital, and the first version, `lower(btrim(name))`, still accepted double spaces, tabs, non-breaking and zero-width characters and "Пица Наполи" next to "Pica Napoli"). Not covered: homoglyphs that are not the Cyrillic letter's phonetic twin (a Cyrillic "Р" that looks like a Latin "P" maps to "r") and respellings ("dj" for "đ", "c" for "č"); diacritics are kept, so "Šumadija" and "Sumadija" are different names, and **only among non-archived restaurants**: an archived restaurant is invisible and can never return (no restore), but keeps its row and name for its customers' history, so counting it would leave an owner unable to reuse the name of a restaurant they "deleted" with no way to see why. That combination (expression + partial) can't be a table-level `UNIQUE` constraint, so it is a unique index; it raises the same `23505`. The "Dodaj restoran" form and the edit form's rename map it to "Restoran sa tim nazivom već postoji." by the index name (`isRestaurantNameTaken()` in `src/lib/restaurant-name.ts`, the same tell-them-apart-by-name approach as the edit form's check-constraint handling), instead of the generic failure. No existing duplicates on the dev project when it was applied; a project that has some would have to rename them before the migration can run.
- Payments (Stripe, **test mode / demo only**): Stripe doesn't operate in Serbia, so this can never go live as-is. It is a sandbox demo: no real money, no real Serbian bank accounts. **No marketplace split** - every payment goes to one platform Stripe account (an optional 5%/95% Connect split was designed and dropped as not worth it). **Pay first, book after** (user decision, replacing an earlier book-then-pay flow): a reservation *with an order* is created only once its payment has succeeded. Flow: the reservation form calls `create-checkout` instead of `create_reservation()`; the function reads the customer's own draft order as the caller (RLS), computes the amount **server-side** from `order_items`, **dry-runs the booking** (`validate_booking()` - `create_reservation()` run and rolled back, so a closed restaurant, a full slot or a taken table is refused with the usual Serbian message *before* any payment), opens a hosted Checkout Session (35-minute expiry, card only, no adaptive pricing, order id in `metadata`) and stores the booking request and the priced total on the draft order (`set_order_pending_booking`). No reservation exists yet. `stripe-webhook` (signature verified) calls `finalize_paid_booking()`, which re-checks the cart still adds up to the priced total and then runs the real `create_reservation()` **as the customer** (transaction-local JWT claims set from the order's `customer_id` and restored afterwards, so every rule - role, hours, capacity, tables, cart availability - applies exactly as before) and marks the order paid, in one transaction. If the booking can't be made after all - the slot was taken while the customer was on the Stripe page (nothing holds it), the time passed, the cart was edited on another tab - it records why on the draft order (`booking_failure`), returns `'failed'`, and the webhook **refunds the payment automatically**; the reserve page then says so and the cart is still there to try again. Any Checkout Session of an awaiting order is accepted (a second, different payment for an already-booked order is `'stray'` and refunded), so two tabs or an `expire()` that loses a race can't leave a customer charged with nothing booked. Stripe returns the customer to the restaurant's reserve page (`?payment=success|cancelled&order=`), which reads the order's real state under RLS (booked / failed+refunded / still processing - the page polls for up to ~30 s while the webhook finishes / backed out) instead of trusting the URL. Amounts are charged in **EUR at a fixed rate** (`RSD_PER_EUR`, default 117) because RSD settlement isn't verified for a test account; `PAYMENT_CURRENCY=rsd` switches to direct RSD once a test call proves it works. Payment state lives on `orders` (`payment_status`, Stripe ids, `pending_booking`, `checkout_total_para`, `booking_failure`), select-only for clients like the rest of `orders`, written by `service_role`-only `security definer` functions - never trusted from the browser. **Refund policy** (user decision): the restaurant's owner cancelling always refunds (any status, incl. "cancel all"); a customer cancelling refunds only while the reservation is `confirmed`, not once it is `preparing_order`/`order_prepared`. `cancel_reservation()` decides this in the same transaction (off the status under its row lock) by setting `refund_pending`; a separate `refund-order` Edge Function does the Stripe refund (idempotency key per order; a refund Stripe reports as already done counts as success) and is argument-free - it refunds whatever `refund_pending` orders the caller can see, so it's also the retry button ("Ponovi povraćaj novca") and the follow-up to "cancel all"; cancelling always calls it when the reservation has an order. `delete_my_account()` / `delete_restaurant()` are refused while an order is `refund_pending` (deleting would remove the only people who can retry it). `STRIPE_SECRET_KEY` must be an `sk_test_`/`rk_test_` key or the functions refuse to run; the Stripe SDK is pinned to `22.6.2`. **Consequences of pay-first:** there is no "pay later" - the old "Plati porudžbinu" button is gone and orders that were confirmed before this change stay "Nije plaćeno" (test data); there is no slot hold while paying, so a booking can be refused *after* payment (and refunded); an order under about 58.5 RSD can't be paid (Stripe's 0.50 EUR minimum); `refund-order` refunds at most 50 pending orders per call. **Not done / known gaps:** refunds issued from the Stripe dashboard aren't tracked (no `charge.refunded` handler); no-show/uncollected orders are never refunded; `supabase/tests/190-order-payments.sql` runs in CI only (no Docker locally) - the SQL logic was smoke-tested on the dev DB with rolled-back scripts. Live-payments research (2026-09-20): Adyen for Platforms and Mollie don't support Serbia; Serbian bank acquirers and AllSecure are single-merchant only; Monri/WSPay MarketPlace advertises sub-merchant payouts and serves Serbia (RSD/sandbox unconfirmed); a platform that forwards owners' money likely needs an NBS payment-institution licence.
