# Database Schema Reference

A human-readable snapshot of the current Supabase/Postgres schema, grouped by
feature instead of by migration date. **This file is generated by reading
`supabase/migrations/` — it is not itself a source of truth and is not run
against the database.** If it ever disagrees with the migrations, the
migrations win; re-generate this file rather than trusting it blindly.

Every table has Row-Level Security (RLS) enabled and no table is reachable via
the Data API until explicitly `grant`ed — Supabase's "auto-expose new tables"
setting is off project-wide, so every table below has its access spelled out
in its own migration on purpose, not by default.

## How to read this

- **Columns** — the current shape, not the history of `alter table` calls that built it.
- **RLS** — who can select/insert/update/delete, in plain English.
- **Functions** section at the bottom — every `security definer` RPC in one place, since that's the actual business logic layer (see below for why they live in migrations at all).

## Auth & Profiles

### `profiles`
One row per `auth.users` row — the signup fields Supabase Auth doesn't store itself.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | = `auth.users.id`, cascades on user delete |
| `first_name`, `last_name`, `phone` | text | required |
| `role` | text | `customer` \| `employee` \| `owner` |
| `created_at` | timestamptz | |

**RLS:** a user can select/update only their own row. There's no insert policy at all — rows are created only by the `handle_new_user()` trigger (see Functions), never directly by a client. An additional narrow policy (added when staff management shipped) lets an owner select the profile of anyone with a `restaurant_staff` row at one of their restaurants, via the `is_restaurant_owner_of_employee()` function — added as a function specifically to avoid an RLS recursion bug (see the callout at the bottom).

## Restaurants & Hours

### `restaurants`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | |
| `owner_id` | uuid FK → `auth.users` | not unique — one owner can have several restaurants |
| `name` | text | |
| `capacity` | integer, nullable | plain manual cap; `null` = unlimited. **Only meaningful/written when the restaurant has no sections and no active layout** — once either exists, effective capacity is computed live from them instead (app logic, see `src/lib/capacity-cascade.ts`) and this column is left stale on purpose. |
| `default_stay_minutes` | integer, not null, default 90 | constrained to 30–180, matching `create_reservation()`'s own duration cap |
| `created_at` | timestamptz | |

**RLS:** select is open to any authenticated user (any role — needed so customers/employees can browse). Insert is restricted to accounts with `profiles.role = 'owner'`. Update/delete restricted to the owning `owner_id`.

### `restaurant_hours`
One row per open interval (not per day) — a day can have multiple rows (split shifts), and an interval can run across midnight as two adjacent rows on neighboring days.

| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK → `restaurants`, cascade | |
| `day_of_week` | smallint 0–6 | Postgres `extract(dow ...)` convention: 0 = Sunday |
| `start_minute`, `end_minute` | smallint 0–1440 | minutes since midnight; `end > start`; 1440 = runs to exact midnight |

**RLS:** select open to all authenticated users; insert/update/delete restricted to the restaurant's owner.

> This table went through two schema revisions (`open_time`/`close_time` + `is_24h`/`closes_next_day` flags → plain `start_minute`/`end_minute` intervals) before landing here — a good example of "the migrations are history, this doc is the destination."

## Staff / Employee Applications

### `restaurant_staff`
One row per (restaurant, employee) pair.

| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK → `restaurants`, cascade | |
| `employee_id` | uuid FK → `auth.users`, cascade | |
| `status` | text | `pending` \| `accepted` — **no `rejected` status**: a reject or a cancel just deletes the pending row |
| unique | `(restaurant_id, employee_id)` | |

**RLS:** an employee sees their own applications; an owner sees applications to their own restaurants. Insert restricted to `profiles.role = 'employee'`, always starting `pending`. The only update path is an owner flipping `pending → accepted` for their own restaurant. Delete covers both an employee cancelling their own pending row and an owner rejecting/removing any row at their restaurant.

## Sections & Table Layout

Two independent, optional features — a restaurant can have sections, a table layout, both, or neither (see `ISSUES.md`'s "Decided" notes for the full reasoning).

### `sections`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK → `restaurants`, cascade | |
| `name` | text | unique per restaurant |
| `capacity` | integer, `>= 0` | manually typed **only** when no active layout exists; once one does, effective capacity is the live sum of that section's tables' seats instead |
| `color_index` | smallint 0–7 | index into the fixed 8-color palette in `src/lib/section-colors.ts` — only the index is stored, never a literal color, so hues can be retuned without a migration |

**RLS:** select open to all; insert/update/delete restricted to the restaurant's owner.

### `layouts`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK → `restaurants`, cascade | |
| `name` | text | unique per restaurant |
| `is_active` | boolean | **multiple layouts can be active at once** (e.g. one per floor) — capacity is derived from the union of every active layout's tables |

**RLS:** same owner-write / any-authenticated-read pattern as `sections`.

### `tables`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK → `restaurants`, cascade | |
| `layout_id` | uuid FK → `layouts`, cascade | |
| `section_id` | uuid FK → `sections`, **set null** on delete | nullable even once the restaurant has sections — "every table needs a section once any exist" is an app-level rule, never a DB constraint |
| `name` | text | unique per **layout**, not per restaurant (two tables in different layouts, or two tables restaurant-wide, may share a name) |
| `seats`, `x`, `y`, `width`, `height` | integer, all positive | grid units for the floor-plan canvas; every table is an axis-aligned rectangle, no rotation |

**RLS:** select open to all. Insert/update additionally verify — not just that `restaurant_id` is owned by the caller, but that `layout_id` and `section_id` actually belong to *that same* restaurant. This was a real fix (see the callout below): without it, an owner could attach their own table to another owner's layout/section, since layout/section ids aren't secret.

## Reservations

### `reservations`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id`, `customer_id` | uuid FK, cascade | |
| `party_size` | integer, `> 0` | |
| `starts_at`, `ends_at` | timestamptz | `ends_at > starts_at`, capped at 24h |
| `status` | text | `confirmed` \| `cancelled` \| `completed` \| `no_show` (only `confirmed` is actually produced by app code today) |

**RLS:** only `select` is granted to `authenticated` — **there is no insert/update/delete grant at all.** The only way a reservation is ever created is `create_reservation()` (see Functions), which runs as `security definer` and writes despite the missing grant. This is deliberate: it's the one place hours/capacity/conflict validation happens, and skipping it isn't possible from a raw client call. Select policies cover the customer who owns it, the restaurant's owner, and its accepted staff.

### `reservation_tables`
One row per table a reservation occupies (several for a multi-table booking).

| Column | Type | Notes |
|---|---|---|
| `reservation_id`, `table_id` | uuid FK, cascade | |
| `starts_at`, `ends_at` | timestamptz | denormalized copy of the parent reservation's range — required because the exclusion constraint below needs both columns on the same row |
| — | **exclusion constraint** | `exclude using gist (table_id with =, tstzrange(starts_at, ends_at) with &&)` — this is the actual double-booking prevention, enforced by Postgres itself, not application code |

**RLS:** select-only, scoped to the reservation's customer/owner/accepted-staff, same shape as `reservations`.

### `reservation_sections`
Used only when a restaurant has sections but no active layout (once a layout is active, tables carry the section instead).

| Column | Type | Notes |
|---|---|---|
| `reservation_id`, `section_id` | uuid FK, cascade | |
| `party_size` | integer, `> 0` | this reservation's share of that section — several rows per reservation when a party spills across sections |

**RLS:** same select-only shape as the two tables above.

> **Deletion/capacity guards:** `reservation_tables.table_id` and `reservation_sections.section_id` are both `on delete cascade` from `tables`/`sections` — deleting either would otherwise silently strip a confirmed, not-yet-ended reservation's seating with no trace. Four triggers close this (see Functions below): deleting a `tables`/`sections` row is rejected outright while a `confirmed` reservation with `ends_at >= now()` still references it, and shrinking `restaurants.capacity`/`sections.capacity` is rejected below the peak already-committed load (summed across overlapping confirmed, not-yet-ended reservations, not just checked one at a time). "Active"/"peak load" both use the same time-based rule as the customer reservations page (`status = 'confirmed' and ends_at >= now()`). The delete-blocking triggers' raised messages name the specific table/section and its earliest active reservation's date/time and party size, rather than a generic "can't delete" string. Two more functions, `tables_with_active_reservations`/`sections_with_active_reservations`, let the owner's edit form (`edit-restaurant-form.tsx`) check every candidate id *before* attempting any delete, so one save reports every blocking table/section at once instead of failing on the first one a trigger happens to hit.

## Menu

### `menu_categories`
`restaurant_id`-scoped, `name` (unique per restaurant) + `display_order` (owner-controlled via reorder buttons, no gap-free requirement).

### `menu_items`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id` | uuid FK, cascade | |
| `category_id` | uuid FK → `menu_categories`, **set null** on delete | nullable — items can be uncategorized |
| `name`, `description` | text | |
| `price` | numeric(10,2), `>= 0` | no currency column — RSD assumed, app is Serbian-only elsewhere too |
| `image_url` | text, nullable | **no owner upload UI yet** — when null, `MenuItemImage` renders an inline SVG placeholder client-side instead of a stored default image |
| `is_available` | boolean, default true | |
| `display_order` | integer | |

### `menu_item_options`
A modifier group on one item (e.g. required single-select "Veličina"). `menu_item_id` FK, cascade. `is_required`, `allow_multiple` booleans. No `restaurant_id` column — ownership is checked by joining up through `menu_item_id`.

### `menu_item_option_choices`
The actual pickable values within a group (e.g. "Mala"/"Srednja"/"Velika"). `option_id` FK, cascade. `price_delta numeric(10,2)` applied on top of the item's base price.

**RLS for all four menu tables:** select open to any authenticated user; insert/update/delete restricted to the owner, verified by joining all the way up to `restaurants.owner_id`. `menu_items.category_id` and `menu_item_options`/`_choices`'s parent references get the same same-restaurant cross-check as `tables.layout_id`/`section_id` above.

## Orders (Cart)

The customer-ordering flow: browse menu → build cart → confirm cart + reservation together in one atomic step. See `ISSUES.md`'s "Customer ordering" Decided notes for the full design story.

### `orders`
| Column | Type | Notes |
|---|---|---|
| `restaurant_id`, `customer_id` | uuid FK, cascade | |
| `status` | text | `draft` \| `confirmed` |
| `reservation_id` | uuid FK → `reservations`, **no cascade** (default RESTRICT) | an order is a financial record — shouldn't vanish if reservation deletion is ever added |
| `confirmed_at` | timestamptz, nullable | |
| — | **partial unique index** | `(customer_id) where status = 'draft'` — a customer has at most **one** draft order at a time, restaurant-agnostic; starting a cart at a different restaurant replaces the old one |

**RLS:** select-only grant, same reasoning as `reservations` — every write goes through `start_cart()`/`add_order_item()` (cart building) or `create_reservation()` (finalizing). Drafts are private to the customer; owners/staff only see `confirmed` orders (a draft is a private basket, like an un-placed Wolt cart).

### `order_items`
| Column | Type | Notes |
|---|---|---|
| `order_id` | uuid FK → `orders`, cascade | |
| `menu_item_id` | uuid FK → `menu_items`, **set null** on delete | historic lines survive a menu item being deleted later |
| `item_name`, `unit_price` | text / numeric | **snapshots** taken at add-to-cart time, computed server-side by `add_order_item()` — never client-supplied |
| `quantity` | integer, `> 0` | the *only* thing a customer can change after adding a line |

**RLS:** select scoped like `orders`. Update/delete allowed only while the parent order is still `draft`. The update policy only allows quantity to change in practice — see the Functions callout below for how that got enforced (it took three attempts).

### `order_item_choices`
Selected modifier choices for one `order_items` line — `option_name`/`choice_name`/`price_delta` snapshots, purely descriptive (the parent line's `unit_price` already has every delta baked in). Select-only grant; rows are only ever written by `add_order_item()`.

## Functions (`security definer` RPCs)

Postgres functions the frontend calls directly via `supabase.rpc(name, args)`, rather than composing raw table queries. **Written in `supabase/migrations/` alongside the tables** — a function is schema too (`create function` is DDL, same category as `create table`), so it has to be replayable in the same ordered, versioned system as everything else. See the design-chat discussion for the longer version, but short version: once business logic moves into the database (specifically so it can run inside a transaction with row locks and see past RLS on purpose), it inherits the database's own version-control mechanism, not the app's file layout.

`security definer` means the function runs with its *creator's* privileges instead of the caller's — so it can deliberately see through RLS, but only to do the one narrow thing it's written for. Every one of these also sets `search_path = ''` and schema-qualifies every reference (`public.foo`), which is this project's standing convention to avoid search-path hijacking.

A reasonable thing to mention if a mentor asks "did everything work first try" — it didn't, and the fix is visible in the migration history.

## RLS pattern used throughout

Almost every table follows one of two shapes:

1. **Public-read, owner-write:** `select` open to any authenticated user (needed for browsing), `insert`/`update`/`delete` restricted to the resource's owner — used by `restaurants`, `restaurant_hours`, `sections`, `layouts`, `tables`, and all four menu tables.
2. **Function-only-write:** no insert/update/delete grant to `authenticated` at all — every write goes through a `security definer` function. Used by `reservations`, `reservation_tables`, `reservation_sections`, `orders`, and `order_item_choices`, since these all need validation (hours, capacity, pricing) that a plain RLS policy can't express.

`tables`, `sections`, and `restaurants` are pattern 1 (owner-write directly, no RPC needed for a plain delete/rename) but additionally carry a `before delete`/`before update` trigger layered on top (see the deletion/capacity guards callout above and the Functions table below) — RLS decides *who* can write, the trigger decides whether *this particular* write is safe given other tables' data, the same division of labor `create_reservation()` already uses.

One real bug is worth knowing about since it shows *why* the cross-table checks matter: the original `tables` insert/update policies checked that `restaurant_id` belonged to the caller, but not that `layout_id`/`section_id` belonged to *that same* restaurant — since those ids aren't secret (same public-read policy as everything else), an owner could otherwise attach their own restaurant's table to a different restaurant's layout or section via a direct API call. Fixed in [tables_rls_verify_layout_and_section_restaurant.sql](supabase/migrations/20260908110000_tables_rls_verify_layout_and_section_restaurant.sql) — the same pattern was then applied proactively to `menu_items.category_id` and the menu option tables from the start.
